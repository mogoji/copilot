## 一、一分钟看懂这个项目

一句话：**用户提一个问题 → 先去自己的 FAQ 知识库里找证据 → 把证据塞进 prompt 交给大模型 → 流式吐字给前端，并标出引用编号；找不到证据就说「不知道」。**

这就是 **RAG（Retrieval-Augmented Generation，检索增强生成）**。

它解决的痛点很具体：直接问大模型「退款多久到账」，模型会编一个答案（幻觉）。加上检索后，模型只能照着资料念，还能标出「这条来自资料 [1]」，答错了能溯源。

技术栈分工：

| 层 | 选型 | 在这里干的事 |
|---|---|---|
| 前端 | Vue 3 + TS + Vite | 输入框、逐字显示、展示引用来源 |
| 后端 | Python 3.12 + FastAPI + uvicorn | 提供 HTTP 接口、把 SSE 流从大模型转发给前端 |
| 向量库 | PostgreSQL 16 + pgvector（Docker） | 存 1024 维向量，算余弦相似度 |
| 模型 | 智谱 `embedding-3`（向量）+ `glm-5.3-flash`（对话） | 文本转向量 / 生成回答 |
| 包管理 | uv | 装依赖、跑脚本（`uv run ...`） |

## 二、两条链路（必须先分清）

这是整个项目最容易被初学者搞混的地方：**同一个知识库，有两种完全不同的时间线。**

### 链路 A：离线灌库（跑一次就够，数据变了再跑）

```
app/data/faq.json  ──读──►  ingest.py
                              │ ① 每条 FAQ 拼成 "问：xx\n答：xx"
                              │ ② 调 embedding-3 批量转向量（1024 维）
                              │ ③ TRUNCATE 两张表（可重复执行）
                              ▼
                    PostgreSQL + pgvector
                    documents(id,title,source)   ← 一条 FAQ 一行
                    chunks(id,doc_id,content,embedding)
```

### 链路 B：在线问答（每次提问都走）

```
浏览器 App.vue
   │ POST /chat/stream  {"q": "退款多久到账？"}
   ▼
main.py  chat()
   │ ① retrieve(question, top_k=5)  ──►  rag.py
   │                                        │ embed_one(question) → 1024 维
   │                                        │ SQL: ORDER BY embedding <=> 向量 LIMIT 5
   │                                        ▼
   │                                    pgvector 返回 Top-5（含 similarity）
   │ ② 阈值过滤：丢掉 similarity < 0.60 的
   │ ③ 拼 system prompt：只许照资料答 + 标 [n] + 没资料就说不知道
   ▼
智谱 GLM（stream=true）
   │ 逐 token 返回
   ▼
main.py gen() 把 token 包成 SSE 帧  ──►  浏览器逐字渲染
```

两条链路的**唯一交点**是那张 `chunks` 表：A 写，B 读。

## 四、文件之间的依赖关系

**真实 import 关系（可以用 `grep "^from\|^import" 逐个核实）：**

```
frontend/src/App.vue
   └── HTTP POST ──► app/main.py
                        └── from app.rag import retrieve ──► app/rag.py
                                                                 └── psycopg ──► PostgreSQL
app/ingest.py ──── psycopg ──► PostgreSQL
             └─── httpx ────► 智谱 /embeddings
app/eval_retrieval.py ── from app.rag import retrieve ──► app/rag.py
app/eval_e2e.py ──────── HTTP ──► app/main.py（必须先启动服务）
app/test_embed.py ────── httpx ──► 智谱 /embeddings（独立，不依赖项目内其他文件）
```

三条要点：

1. **只有 `main.py` 会 import `rag.py`**，方向是单向的：接口层 → 检索层 → 数据层。反过来不行，否则就循环依赖了。
2. **`ingest.py` 和 `main.py` 互不认识**，它们只通过数据库里的表通信。这是「离线/在线」解耦的典型做法。
3. **`app/rag.py` 与 `backend/rag.py` 是同一份代码的两个版本**，后者是拆分目录前的残留。初学者最容易在这里改错文件——改了 `backend/rag.py` 发现没生效，就是因为没人 import 它。

## 五、逐文件详解

### 5.1 `app/main.py` — HTTP 门面 + SSE 转发

**职责**：对外只暴露两个接口，把「检索 → 过滤 → 拼 prompt → 流式转发」串起来。

**模块级变量 / 常量**

| 名字 | 值 | 作用 |
|---|---|---|
| `app` | `FastAPI()` 实例 | ASGI 应用，uvicorn 启动的就是它 |
| `GLM_URL` | `https://open.bigmodel.cn/api/paas/v4/chat/completions` | 上游对话接口（OpenAI 兼容格式） |
| `GLM_MODEL` | `"glm-5.3-flash"` | 用哪个模型 |
| `EVIDENCE_TH` | `0.60` | **证据阈值**：相似度低于它就不喂给模型。这是防幻觉的第一道闸，取值靠 70 条评测集实测校准：45 条应命中用例 top1 最低 0.628 / 中位 0.714 / 最高 0.796；10 条**域外**拒答用例 top1 最高 0.563，空档 0.563~0.628，0.60 落在中间（命中零误杀、域外零误放）。**但它对「域内硬负例」无效**：15 条「问的是售后、库里确实没答案」的用例有 13 条 ≥ 0.60，与命中分布重叠；要让它们全挡住，阈值得提到 0.73，同时误杀 31/45 条命中。所以 0.60 只是域外护栏，域内靠 prompt 兜底——别指望调这个数解决幻觉 |

**导入细节（两处小瑕疵，读代码时别被绕晕）**：`json` 在第 3 行和第 30 行各 import 了一次；`asyncio` 导入了但没用到。这不影响运行，但说明文件是在迭代中长出来的。

**中间件**

```python
app.add_middleware(CORSMiddleware, allow_origins=["http://localhost:5173"], ...)
```
Vite 开发服务器跑在 5173，FastAPI 跑在 8000，**端口不同 = 跨域**。不加这段，浏览器会拦掉请求并报 CORS 错误。`allow_origins` 写死具体地址而不是 `*`，是为了将来上生产不误开。

**函数 1：`health() -> dict`**

```python
@app.get("/health")
def health():
    return {"ok": True}
```
探活接口。作用不是「给用户看」，而是**给你自己排障时用**：`curl localhost:8000/health` 能通，说明服务活着，问题在别处。

**函数 2：`async def chat(body: dict) -> StreamingResponse`**（核心）

逐段拆：

| 行 | 代码 | 说明 |
|---|---|---|
| L50 | `question = body.get("q", "")` | 从 JSON 请求体取问题。用 `.get` 带默认值，缺字段也不 500 |
| L52 | `hits = retrieve(question, top_k=5)` | **检索**，返回 5 条候选（含 `content` / `similarity`） |
| L54 | `th = float(body.get("evidence_th", EVIDENCE_TH))` | 阈值可被请求体覆盖。这样不用改代码重启就能对比 0.35 vs 0.60——**为了做 A/B 评测而设计的参数** |
| L55 | `good = [h for h in hits if h["similarity"] >= th]` | **过滤**：留下真证据。可能为空列表 |
| L57-59 | `evidence = "\n".join(f"[{i}] {h['content']}")` | 把证据拼成带编号的文本块，编号就是模型要引用的 `[1] [2]` |
| L60-61 | `sources = [{index, content, similarity}]` | 同一批证据的**结构化版本**，单独发给前端渲染「参考资料」区 |
| L64-68 | `system = ...` | System prompt 三段约束：①只根据资料 ②标引用编号 ③没资料就说不知道。注意 L67 处理了证据为空的情况（`（无相关资料）`） |
| L70 | `async def gen()` | **异步生成器**，SSE 的核心。每次 `yield` 就是推一帧给浏览器 |
| L71-73 | 先 yield `{"sources": [...]}` | 先发引用，前端可以先画出处、再等正文 |
| L74-85 | `headers` / `payload` | `stream: True` 是流式的开关；`messages` 里 system + user 两条 |
| L87 | `httpx.AsyncClient(timeout=60)` | **异步**客户端，不能用 `httpx.post()` 同步版，否则会阻塞整个事件循环 |
| L88 | `client.stream("POST", ...)` | 流式请求上下文 |
| L89 | `async for line in r.aiter_lines()` | 一行一行读上游 SSE |
| L90-91 | `if not line.startswith("data: "): continue` | SSE 格式是 `data: {json}`，其它行（空行、注释）跳过 |
| L92 | `chunk = line[6:]` | 砍掉 `"data: "` 这 6 个字符 |
| L93-94 | `if chunk.strip() == "[DONE]": break` | 上游的结束标记 |
| L95-98 | `try: json.loads(chunk) except: continue` | 容错：偶尔会收到不完整帧，跳过即可，不能让整个流崩掉 |
| L99-102 | `choices[0].delta.content` | 只取增量文本，`or ""` 兜住 None |
| L103-104 | `yield {"token": token}` | 把上游格式**转成自己的格式**再发前端 |
| L105-106 | `except Exception as e: yield {"error": str(e)}` | 出错也走 SSE 帧，前端能显示错误而不是干等 |
| L107 | `yield "data: [DONE]\n\n"` | 自己的结束标记 |
| L108 | `StreamingResponse(gen(), media_type="text/event-stream")` | `text/event-stream` 是 SSE 的 MIME 类型，缺了浏览器不会当流处理 |

**为什么必须用生成器 + StreamingResponse？**
如果先 `await` 拿完整回答再 return，用户要盯着空白页等 3~5 秒。生成器让你「拿到一段就发一段」，首字延迟从秒级降到毫秒级。这也是 `async` 的理由：等待上游 IO 时事件循环能去处理别的请求。

**这个文件里值得记住的 3 个设计**
1. 密钥只在后端：`os.getenv('GLM_API_KEY')`。前端永远看不到 Key。
2. 双保险防幻觉：阈值过滤（代码层）+ prompt 约束（模型层）。只有一层都不够稳。
3. 协议转换：上游是 OpenAI 格式，前端只认 `{sources}` / `{token}` / `{error}`。中间这层翻译让前后端解耦。

### 5.2 `app/rag.py` — 检索层（项目的心脏）

**职责**：一句话进，最相关的 K 条资料出。它**不生成任何文字**，只负责「找」。

**常量**

| 名字 | 作用 | 注意 |
|---|---|---|
| `EMB_URL` | 智谱向量接口 | 和对话接口是**两个不同的 URL** |
| `HEADERS` | 带 Bearer Key 的请求头 | 在模块导入时就求值，所以 `load_dotenv()` 必须在它上面（L5-6 已保证） |
| `DB_DSN` | 数据库连接串 | **密码硬编码在代码里**（见第七节问题清单） |

**函数 1：`embed_one(text) -> list[float]`**

```python
r = httpx.post(EMB_URL, headers=HEADERS,
               json={"model": "embedding-3", "input": text, "dimensions": 1024}, timeout=30)
return r.json()["data"][0]["embedding"]
```
- `dimensions: 1024` **必须和建表时的 `vector(1024)` 一致**，否则插入/查询直接报维度错误。
- `data` 是数组，单个输入取 `[0]`。
- 返回的是长度 1024 的浮点列表，例如 `[0.0123, -0.0456, ...]`。
- 这一步是**同步阻塞**调用。当前代码在异步路由里直接调用它，会短暂阻塞事件循环——小流量没事，量大时应该换成 `httpx.AsyncClient`。

**函数 2：`retrieve(question, top_k=5) -> list[dict]`**（线上真正在用的）

```python
vec = embed_one(question)
vec_str = "[" + ",".join(str(x) for x in vec) + "]"     # pgvector 只认 [0.1,0.2,...] 字符串
...
"SELECT content, 1 - (embedding <=> %s::vector) AS similarity "
"FROM chunks ORDER BY embedding <=> %s::vector LIMIT %s"
```

三个关键点：
1. **`<=>` 是 pgvector 的余弦距离算子**，范围 0~2，越小越像。
2. **`1 - 距离 = 相似度`**，所以 `0.78` 表示比较像。这个换算是理解所有阈值的前提。
3. **同一个向量参数传了两次**（SELECT 里算分、ORDER BY 里排序）。`%s::vector` 的 `::vector` 是类型转换，不写会报「operator does not exist」。
4. `ORDER BY ... LIMIT` 会走 `chunks` 表上的 HNSW 向量索引，20 条数据看不出差别，数据量上万后是数量级差异。

返回值：`[{"content": "...", "similarity": 0.7834}, ...]`，最多 `top_k` 条。**注意它一定会返回 K 条**，哪怕全都不相关——这正是需要在 `main.py` 里做阈值过滤的原因。

**函数 3：`retrieve_keyword(question, top_k=10)`**（关键词通道，待启用）

- 内嵌 `bigrams(s)`：把字符串切成所有相邻两字组合，`"退款到账"` → `{"退款","款到","到账"}`。中文不按空格分词，bigram 是最省事的近似。
- `qg & cg` 交集 = 共同双字组；`qg | cg` 并集。
- `overlap = 交集 / 并集` = **Jaccard 相似度**，`max(1, ...)` 防除零。
- `cg = bigrams(content[:80])`：只取每条切片前 80 字，注释说大致覆盖「问句 + 答案开头」，同时也控制了计算量。

**函数 4：`retrieve_hybrid(question, top_k=5, rrf_k=60)`**（混合检索，待启用）

RRF（Reciprocal Rank Fusion）的思想：**不看分数高低，只看排名**。
每条结果得分 = `1 / (60 + 名次)`。第 1 名得 1/61，第 2 名 1/62……两路（向量、关键词）的分数相加，谁两路都靠前谁胜出。

- `scores`：`defaultdict(float)`，按内容文本累加排名分。
- `sim_of`：记录原文的向量相似度，因为 RRF 分不能当相似度用（量级完全不同）。
- `rrf_k=60` 是论文里的经验值，作用是压平头部差距，避免某一路的第 1 名一票独大。

**为什么写好了却没启用？** 项目 README 有诚实记录：20 条 FAQ 的小样本上，向量检索 recall@5 已经是 1.0，加 bigram 反而把「订单详情」这种高频词当成强相关，**指标略降**（0.978）。所以保留代码、注释掉调用，等语料含型号/编号这类专有名词时再开。**这是很好的工程习惯：不为好看编数据，而是保留开关 + 记录边界条件。**

**`if __name__ == "__main__"` 块**：直接 `python app/rag.py` 就能跑两个样例问题，打印相似度和前 40 字。写检索代码时，这个自测入口比开服务快得多。

### 5.3 `app/ingest.py` — 离线灌库

**函数 1：`embed(texts) -> list[list[float]]`**

```python
r = httpx.post(..., json={"model": "embedding-3", "input": texts, ...})
d = r.json()
if "data" not in d:
    raise RuntimeError(f"embedding 失败: {d}")
return [item["embedding"] for item in sorted(d["data"], key=lambda x: x["index"])]
```
两个细节值得学：
1. **先校验再取值**：接口失败时 `data` 不存在，直接 `["data"]` 会抛难以理解的 `KeyError`，主动抛带原始响应的异常才对得起调试的自己。
2. **按 `index` 排序**：批量接口**不保证返回顺序**，但你必须按输入顺序取（否则 FAQ#1 的向量会配到 FAQ#7 的文本上）。这是批量调用 embedding 最经典的坑。
3. `timeout=60`（单条只要 30）：批量慢得多。
4. 单请求有数量上限（约 64 条），20 条可以一次发，量大必须分批。

**函数 2：`main() -> None`**

流程四步：
1. `json.load(open("app/data/faq.json", encoding="utf-8"))` —— **相对路径，所以必须在 `backend/` 目录下运行**，这是 README 里记过的坑（`FileNotFoundError`）。更稳的写法是用 `Path(__file__).parent / "data" / "faq.json"`。
2. `texts = [f"问：{f['q']}\n答：{f['a']}" for f in faqs]` —— **Q 和 A 拼在一起向量化**。原因：用户提问时的措辞更接近「问」，答案里才有「答」里的关键实体，一起编码命中率更高。这就是「切片策略」最简单的形态。
3. `TRUNCATE chunks, documents RESTART IDENTITY CASCADE` —— 清空且重置自增 ID，`CASCADE` 连带清子表。这让脚本**可重复执行**（幂等），不会越跑越多。
4. 循环：先插 `documents` 拿 `RETURNING id`，再用这个 `doc_id` 插 `chunks`。**一张 FAQ = 一个 document + 一个 chunk**（`chunk_index=0`）。真实文档要按长度切多个 chunk，这里数据太短就简化了。

> **事务边界（L26 / L27 / L39）**：本机实测 psycopg 3.3.9 的 `Connection.__exit__` 源码——`with psycopg.connect(...)` 在**正常退出时自动 `commit()` 并关闭连接，抛异常则 `rollback()`**。所以 L39 的 `conn.commit()` 是冗余但无害的，删掉也能跑；`with conn.cursor()` 只负责关闭游标。真正要理解的是：TRUNCATE 与 41 次 INSERT 全在**同一个事务**里，中途任何一步失败都会整体回滚，不会出现「旧数据清空了、新数据只进了一半」。这也是 PostgreSQL 相比 MySQL 的一个重要特性：TRUNCATE 本身可回滚。

### 5.4 `app/eval_retrieval.py` — 检索层评测

**为什么要有它**：改检索逻辑（换模型、改 top_k、加 hybrid）之后，你怎么知道变好还是变坏？靠感觉不算数，要有数字。

**L9 `sys.path.insert(0, str(Path(__file__).resolve().parent.parent))`**
用 `python app/eval_retrieval.py` 运行时，`sys.path[0]` 是 `app/`，`from app.rag import` 找不到 `app` 包。这行把 `backend/` 插到搜索路径最前面。**这是 Python 脚本「按文件位置定位」的标准补救手法**，比 `cd` 来 `cd` 去可靠。

**`load_cases(path=None) -> list[dict]`**
读 `.jsonl`（每行一个 JSON），`if l.strip()` 跳过空行。路径默认也基于 `__file__` 计算，换目录跑不会挂。

**`evaluate(top_k=5, reject_th=None) -> dict`**

> `reject_th` 默认取 `config.EVIDENCE_TH`（默认 0.60），与线上检索证据阈值单一来源；需要复现历史基线时可显式传参覆盖。

累积变量：

| 变量 | 含义 |
|---|---|
| `hit_ok` / `hit_total` | 命中的用例数 / 应命中的总数（hit + boundary） |
| `rej_ok` / `rej_total` | 正确拒答数 / 应拒答总数 |
| `rr_sum` | 倒数排名累加（Reciprocal Rank），用于算 MRR |
| `top_score` | 本次检索的最高相似度 |
| `rank` | gold 关键词第一次出现的位置（1 开始）；没出现是 `None` |

判定逻辑：
- `expect` 是 `hit` 或 `boundary` → 在返回的 5 条里找 `c["gold"]` 是否出现在正文中，找到就 `+1`，并累加 `1/rank`。
- `expect` 是 `reject` → 看 `top_score < reject_th`，是则算「检索层能识别出无关」。

三个指标：

| 指标 | 公式 | 直觉解释 |
|---|---|---|
| `recall@5` | `hit_ok / hit_total` | 前 5 条里有没有正确答案 |
| `mrr` | `rr_sum / hit_total` | 正确答案排得越靠前越高，第 1 名 = 1.0 |
| `retrievable_reject` | `rej_ok / rej_total` | 无关问题能不能被相似度识别出来 |

> `reject_th` 已统一为 `config.EVIDENCE_TH`（默认 0.60），不再在本文件写死 0.65，避免同一概念出现两个数字的维护隐患。

### 5.5 `app/eval_e2e.py` — 端到端评测

和上一个的区别：它**真的去调 `/chat/stream`**，所以能测到「模型答得对不对、有没有标引用、拒答话术对不对」。代价是慢（70 条实测约 5 分半）且花钱。

**阈值从命令行传入**
`uv run python app/eval_e2e.py 0.60`。不传就是 `None`，`ask()` 里就不带 `evidence_th`，用服务端默认值。**这是「同一份代码对比两套参数」的干净做法**，不用改代码重启。

> 解析必须写在 `if __name__ == "__main__":` 里，不能写成模块级的 `TH = float(sys.argv[1])`——否则 `eval_norag.py` import 本模块时，它自己的命令行参数会被当成阈值解析并报 `ValueError`。这是踩过的坑。

**`ask(q, th=None) -> (answer, sources)`**
用 `httpx.stream` 消费 SSE，`data == "[DONE]"` 时 break，遇到 `sources` 就存下来，遇到 `token` 就拼字符串。**注意它和 `main.py` 的 gen() 是对称的**——一个发一个收，读懂一个另一个就懂了。

**`is_hit(gold, ans) -> bool`**
先判 `gold in ans`，不中再退化为「gold 的字按顺序出现」的子序列匹配。原因：纯子串判定会把「填写原因」答成「填写退款原因」、「修改地址」答成「修改收货地址」全判成失败，3 条正确回答被误判、命中率凭空掉 4 个点。

**`evaluate(th=None) -> dict`**
统计：
- `answer_hit_rate`：`gold` 是否命中（答案对不对）
- `citation_rate`：回答里有没有 `[1]` / `[2]`（守不守 prompt 规矩）
- `reject_rate`：拒答类是否说了「没有相关信息」或「联系人工客服」
- `reject_avg_sources`：**拒答时平均塞了几条伪证据**。加入域内硬负例后：0.35 时 4.52 条，0.60 时 1.12 条（不再是 0——硬负例本身就会被检索到，只是模型没被带偏）
- `failures`：失败明细（问题、类型、gold/实际回答前 80 字）。**没有明细的指标，掉点也不知道为什么掉**

> 局限：`"[1]" in ans or "[2]" in ans` 只能测「有没有标」，测不出「标得对不对」。要更严需要解析编号和 sources 做对齐。

**no-RAG 对照组：`app/eval_norag.py`**

单独一个脚本，不走 `/chat/stream`（那条链路必然先检索，关不掉），直接调上游 GLM 的 `messages` 接口。

设计上三个必须对齐、一个必须不同：
- 对齐：同一套 70 条、同一个模型、同一个 `is_hit` 判定器；
- 不同：system prompt **不能**带「只根据资料回答 / 没有就说不知道」，否则它只是「检索为空的 RAG」，仍然拒答，测不出增益。给的是「普通电商客服 + 允许用行业常识」。

实测（`uv run python -m app.eval_norag`，70 条约 17 分钟，非流式比流式慢）：

| 指标 | no-RAG | RAG(0.60) |
|---|---|---|
| `answer_hit_rate` | 0.844 | 1.000 |
| `citation_rate` | 0（无引用机制） | 1.000 |
| 关键词口径拒答率 | 0.000 | 1.000 |
| 硬负例「未编造」（人工复核） | 0/15 | 15/15 |

关键词口径对对照组不公平（它拒了，但说「不在我的服务范围内」），所以 25 条应拒答还做了人工复核：明确拒绝 7、跑题输出 2（写诗、教截屏）、编造具体政策或数字 16。

这就是 RAG 的真实增益：**没有它时，模型不会说「不知道」，而是用别家平台的规则和自己的想象填空**（报京东PLUS 149 元/年、花呗 12 期、48 小时反馈）。

### 5.7 `app/test.py` — 早期草稿（已弃）

功能与 `ingest.py` 相同，但有几处初学者会踩的写法：

```python
def embed(texts):
    json = {                      # ← 变量名 shadow 了 json 模块！
        "model": "embedding-3", ...
    }
```
函数内部 `json` 变成 dict，之后任何 `json.load` 都会 `AttributeError`。虽然这个函数里没用别的 json 功能所以「碰巧能跑」，但这是**命名遮蔽（shadowing）**的典型反例。

其它问题：
- `open("./data/faq.json")` 路径相对 `app/`，只能从 `app/` 里跑，和 ingest.py 的约定不一致。
- `psycopg.connect()` 不带 DSN，依赖环境变量，容易连错库。
- `conn.commit()` 是冗余的：psycopg3 的 `with connect()` 退出时会自动提交，写了不影响正确性。
- 它被 `.gitignore` 里的 `test.py` 规则忽略了，所以**不会进 Git**。留着当草稿可以，但建议改名成 `notes/` 里，避免和新同事解释。

**学到的教训**：不要用 `json`、`list`、`str`、`id`、`type` 当变量名。

### 5.9 数据文件

**`app/data/faq.json`**（20 条）

```json
{"id": 1, "q": "如何申请退款？", "a": "登录账户后进入订单详情，点击申请退款，填写原因并提交。审核通过后款项将在3-5个工作日原路退回。"}
```
`id` 只做可读标识（真正主键是数据库自增 id）；`q`/`a` 会被拼成切片文本。

**`app/data/eval.jsonl`**（55 行，每行一个 JSON）

```json
{"q":"钱什么时候能退回来","expect":"hit","gold":"3-5个工作日","note":"同义改写，测语义检索"}
```

| 字段 | 作用 |
|---|---|
| `q` | 测试问题 |
| `expect` | `hit`（应命中）/ `boundary`（边界，措辞绕）/ `reject`（应拒答） |
| `gold` | **答案原文里的关键词**，用它判断「答对了没」 |
| `note` | 这条用例想测什么（给人看的） |

分布：30 hit + 15 boundary + 25 reject（10 条域外 + 15 条域内硬负例）。

**为什么要有「域内硬负例」**：只用「今天天气怎么样」这种域外问题测拒答，测的是「话题不相关时会不会答」，模型不用什么能力就能过——指标 1.0 是假象。真正会翻车的是「会员一年多少钱」「分期最长几期」这类：问的完全是售后，用的词和 FAQ 高度重叠，但库里确实没这条答案。它们才是幻觉的高发区。

硬负例的造法：拿每条 FAQ 往外扩一层——问它「同属性但库里没写的东西」。会员权益 → 会员价格/能否转让；发票开具 → 能否开个人抬头/丢了能否补开；物流查询 → 能否指定快递/预约周末送。实测这类问题 top1 相似度 0.604~0.729，和命中类（0.628~0.796）几乎完全重叠，**单靠阈值无法区分**。

**两个必须遵守的造数据规则**（README 里踩过坑）：
1. `gold` 必须取自 **FAQ 的答案原文**，不能取问题原文。比如 FAQ#7 答案写的是「直接取消」，用「取消订单」做 gold 会误判。
2. `gold` 要有区分度，别用「订单详情」这种十几条都含的高频词。

## 六、把设计决策串起来看（面试/复盘能用）

| 决策 | 为什么这么做 | 代价 |
|---|---|---|
| 后端代理大模型，不下发 Key | 前端可见 = 任何人能刷你的账单 | 多一层转发 |
| SSE 而不是 WebSocket | 单向推送足够，纯 HTTP，实现简单 | 不能双向通信 |
| 用生成器 `yield` 而非一次性返回 | 首字延迟从秒级到毫秒级 | 错误处理变复杂（要在流里发 error 帧） |
| 向量检索用余弦距离 | 语义相近即可命中同义改写 | 对专有名词/编号不敏感 |
| 阈值 0.60 过滤证据 | 消除「伪证据」，省 token 且降幻觉 | 边界问题可能被误杀 |
| prompt + 阈值双保险 | 单靠任一层都不够稳 | prompt 变长，成本略增 |
| 评测脚本分「检索层 / 端到端」 | 前者秒级免费，改检索时快速回测 | 维护两套代码 |
| hybrid 写好不启用 | 小样本上指标反而降，如实记录 | 代码里有「休眠」分支 |

## 八、初学者重实现路线（8 个阶段）

核心方法：**一次只引入一个新变量，每阶段有独立验收标准。** 当前项目的 README 里叫「分而治之」——出问题时立刻能定位是哪一层，而不是面对黑盒从头查。

### 阶段 0：环境（半天）
- Docker Desktop 起 `pgvector/pgvector:pg16`，`docker ps` 看到 Up。
- `uv --version`、`python --version`（3.12）。
- 建 `.env`，放 Key；`.gitignore` 加 `.env`。
- **验收**：DBeaver 连上 5432，`SELECT 1` 有结果；`echo $GLM_API_KEY` 在脚本里读得到。

### 阶段 1：最小流式闭环（1 天）★ 最关键
先不做 RAG。目标：**前端能逐字显示大模型的回答**。
- 写 `main.py`：`/health` + `/chat/stream`，`stream=True` 直通 GLM，不检索。
- 写 `App.vue`：`fetch` + `ReadableStream` + `buffer.split('\n\n')` 拼半帧。
- **验收**：浏览器输入问题，文字一个字一个字蹦出来。
- **为什么先做这个**：SSE 是整条链路里最容易出错的环节（半帧、`data: ` 前缀、`[DONE]`），单独调试成本最低。等 RAG 接进来再查出问题，就分不清是检索错了还是流断了。

### 阶段 2：验证向量接口（2 小时）
- 写 `test_embed.py`：一个英文句子 → 打印维度。
- **验收**：`len(vec) == 1024`。
- **坑**：Key 错会返回 `{"error": ...}`，先校验 `"data" in d` 再取值。

### 阶段 3：建表 + 灌库（半天）
- 用第七节的 DDL 建 `documents` / `chunks`。
- 抄 20 条 FAQ 到 `faq.json`（自己编售后问题就行）。
- 写 `ingest.py`：读 → 拼「问/答」→ 批量 embed → TRUNCATE → 两条 INSERT。
- **验收**：`SELECT count(*) FROM chunks;` = 20；随机 `SELECT content FROM chunks LIMIT 3;` 内容正确。
- **坑**：批量 embedding 返回顺序不保证 → 必须按 `index` 排序；事务由 `with psycopg.connect()` 在退出时自动提交，无需手动 commit。

### 阶段 4：检索函数（半天）
- 写 `retrieve(question, top_k=5)`，SQL 就一句带 `<=>` 的查询。
- 加 `__main__` 自测，打印相似度。
- **验收**：问「退款多久到账」，第一条相似度 > 0.7 且内容是退款相关；问「今天天气」，最高分 < 0.6。
- **这一步做完，你已经掌握了 RAG 的核心**，剩下的都是工程包装。

### 阶段 5：接进接口 + 阈值（半天）
- `main.py` 里加 `retrieve` → 过滤 → 拼 system prompt → 先发 sources 再发 token。
- **验收**：问售后问题有回答且带 `[1]`；问无关问题回答「没有相关信息」。前端能看到引用来源。

### 阶段 6：先写 6 条评测（半天）
- `eval.jsonl` 先写 6 条：4 hit + 2 reject。
- 写 `eval_retrieval.py`（不花钱）+ `eval_e2e.py`（花钱）。
- **验收**：能输出 `recall@5` / `mrr` / `reject_rate` 三个数字。
- **为什么现在写**：没有数字，你后面每一次「优化」都是自嗨。评测集是玩具 Demo 和正经系统的分水岭。

### 阶段 7：用数据做一次调优（半天）★ 最能讲的一步
- 扩到 70 条（hit 30 / boundary 15 / reject 25，其中 15 条是域内硬负例）。
- 记录阈值 0.35 时的 `reject_avg_sources`（实测 4.52）。
- 只改一个数字 → 0.60 → 重跑同一套用例（实测降到 1.12，命中率不变）。
- **验收**：拒答时的 sources 从 4~5 降到 1 左右，命中率不降。
- **加分动作**：再做一次阈值扫描（0.60/0.65/0.66/0.70/0.73），把「命中误杀数 vs 硬负例拦截数」列成表。你会发现要让硬负例全挡住需 0.73、代价是废掉 31/45 条命中——**能讲出"这条路走不通"，比晒一个漂亮数字更像工程师**。
- **再补一个 no-RAG 对照组**：同一套用例、不做检索，看裸模型能得多少分。实测命中 0.844 vs 1.000、15 条硬负例编造 15 条 vs 0 条。**这是「RAG 到底值不值得上」的唯一硬证据**，比任何主观描述都有说服力。
- 把「发现伪证据 → 定位分界 → 改一个数 → 用数字验证」这个过程记在 README 里。**这是可复现的证据链，比任何形容词都有说服力。**

### 阶段 8：加分项（选做）
- 混合检索 `retrieve_keyword` + RRF（先测指标，降了就照实写「不启用」）。
- LLM rerank：用大模型给 Top-10 重新打分。
- prompt 版本化 + golden set 回归。
- Docker 化后端：`Dockerfile` + compose 里加 `api` 服务，`depends_on: db`。

## 十、一句话总结

这个项目本质上只做了一件事：**把「找资料」和「说人话」拆成两个独立的步骤，中间用一段带编号的文本连起来。**

- 找资料 = 向量化 + 余弦检索 + 阈值过滤（`rag.py`）
- 说人话 = prompt 约束 + 流式生成（`main.py`）
- 保证不出错 = 评测集 + 阈值校准（`eval_*.py`）

重实现时，按这个拆分顺序做，每步都能独立验证——这就是它为什么对初学者友好。
